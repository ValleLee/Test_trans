# SWE-Bench Pro V2 Functional Verifier 转换实验设计

## 1. 实验目标

本实验面向 SWE-Bench Pro V2 中的少量代表性任务，构造一套可复现的 **Functional Verifier 转换流程**。

核心目标不是重新定义任务，而是：

1. 保留原始 `Problem Statement` 作为唯一规范性任务描述；
2. 允许 Converter 读取完整 construction evidence，包括 `P / R / I / F2P / P2P / Gold / Repo / Env`，用于理解历史测试、识别实现绑定和寻找更合理的可观察行为；
3. 将 historical verifier 转换为更 implementation-agnostic 的 functional verifier；
4. 用确定性执行、Positive QA 和 Negative QA 验证新 verifier 既不过严也不过松；
5. 最终在相同 Harbor、相同 agent scaffold、相同 LLM 配置下，对比：
   - A：原始 instruction + 原始 verifier；
   - B：P-only instruction + 原始 verifier；
   - C：P-only instruction + functional verifier。

整体实验分为三个相互独立但顺序衔接的阶段：

```text
Stage 1  数据准备
   ↓
Stage 2  Functional Verifier 转换
   ↓
Stage 3  A / B / C 对比评测
```

---

# 2. 核心原则

## 2.1 Specification 原则

最终规范只由原始 `Problem Statement` 定义：

```text
Normative specification = Problem Statement
```

Converter 可以读取：

```text
P / R / I
historical F2P / P2P
Gold
Repo
Original verifier
Environment
```

但这些信息的地位不同：

```text
P
= 唯一 normative specification

R / I / F2P / P2P / Gold
= construction evidence
= 可以帮助理解和转换
= 不能独立扩张最终 correctness semantics
```

因此，最终 functional verifier 中的语义要求必须能够回溯到原始 Problem Statement。

## 2.2 Instruction 原则

最终：

```text
final/instruction.md
= 原始 Problem Statement
```

不让 LLM 重写 instruction。

`R / I` 不进入最终 instruction。

## 2.3 Agent 与硬规则职责

```text
mini-swe-agent / LLM
→ 探索、理解、创造、语义判断、修复

SCRIPT / Harbor / Docker
→ 下载、执行、schema 检查、Base/Gold replay、回归测试、
   materialize、package、统计
```

同一个 revision 的相同 deterministic validation **只执行一次**。

Hard Validator 的执行结果既是正式 Gate，也是 Converter 的 repair feedback。

# 3. Stage 1：数据准备阶段（Data Preparation）

## 3.1 目标

准备后续转换所需的官方原始数据、运行环境和可复现信息，并首先确认原始 SWE-Bench Pro V2 task 自身有效。

这一阶段只做确定性工作，不运行 Converter。

## 3.2 Pipeline

```text
Selected instance_id list
        │
        ▼
① OFFICIAL REPO / TASK FETCH
   [SCRIPT]
        │
        ├─ clone / update SWE-bench_Pro-os
        │   并固定 upstream commit
        │
        ├─ 获取 v2/tasks/<instance_id>/
        │
        ├─ 保存到 tasks/<id>/original/
        │
        ├─ 获取对应 structured dataset row / metadata
        │
        └─ 记录来源版本信息
        │
        ▼
② IMAGE / ENVIRONMENT PREPARATION
   [SCRIPT + HARBOR / DOCKER]
        │
        ├─ 读取 original task 环境配置
        ├─ resolve 对应 Docker image
        ├─ 本地存在 → reuse
        └─ 本地不存在 → lazy pull
        │
        └─ 记录 image digest
        │
        ▼
③ ORIGINAL ORACLE PREFLIGHT
   [SCRIPT + OFFICIAL HARBOR]
        │
        ├─ Base / Empty + Original verifier
        │      → 必须 FAIL
        │
        └─ Gold / Oracle + Original verifier
               → 必须 PASS
        │
        ├─ FAIL → STOP / REVIEW
        └─ PASS
             │
             ▼
④ PROVENANCE FREEZE
   [SCRIPT]
        │
        ├─ upstream commit
        ├─ dataset revision
        ├─ task hash
        ├─ image digest
        ├─ preflight logs
        └─ source metadata
        │
        ▼
      READY
```

只有 `READY` 的任务进入 Stage 2。

### 当前 100 条执行入口

`task_list/selected_100.txt` 包含原有 20 条；语言数为 Python 40 / Go 36 /
JavaScript 22 / TypeScript 2。前三种语言各选 2 条官方 HARD，TypeScript
不选 HARD；筛选依据在 `task_list/selection_report.json`。当前数据准备脚本在 `dataprepare/` 下，
镜像存入本机 Docker daemon 的 `/data/docker`。依次执行：

```bash

python3 dataprepare/pull_selected_images.py --workers 4
python3 dataprepare/preflight_selected.py --workers 4

```

再重复任务获取、镜像下载和预检，直到最终 100 条全部 READY。

本机用原任务的 `tests/test.sh` 和原镜像逐条执行 Base/Gold 检查；官方
Harbor v0.22.0 源码固定在 `upstream/harbor`，当前 Python 环境未安装 CLI。
`preflight/report.json` 记录本地检查结果，官方 release gate 只能作为来源
参考，不能替代本地 READY 判断。

## 3.3 Stage 1 接受条件

至少满足：

```text
original task fetched       = true
environment runnable        = true
Base / Empty                = FAIL
Gold / Oracle               = PASS
provenance recorded         = true
```

Stage 1 不做任何 verifier 转换。

## 3.4 Stage 1 主要产物

```text
tasks/<id>/original/
data/stage1/<id>/source/
data/stage1/<id>/preflight/
runs/<id>/source/               # Stage 2 selected task only
```

`tasks/<id>/original/` 在 Stage 1 获取时即固定为不可变输入；是否 READY 由
`data/stage1/<id>/preflight/report.json` 和镜像状态决定。Stage 1 证据位于
`data/stage1/<id>/`。只有真正进入 Stage 2 的任务才在 `runs/<id>/` 下创建运行
目录，并将所需 source evidence 移入 `runs/<id>/source/`；Stage 1 未通过的任务不会新建 Stage 2 run。

# 4. Stage 2：Functional Verifier 转换阶段

## 4.1 目标

在不改变 Problem Statement 语义的前提下，把 historical verifier 转换成更 implementation-agnostic 的 functional verifier，并通过 deterministic validation 与正/负 QA 验证其质量。

## 4.2 Pipeline

```text
Stage 1 READY Original Task
P / R / I / F2P / P2P / Gold / Repo / Env
                         │
                         ▼
              ① FUNCTIONAL CONVERTER
                 [mini-swe-agent]
                         │
                 读取全部 construction evidence
                         │
              P = normative specification
         其他材料 = construction evidence
                         │
                         ▼
        ┌──────── Converter Revision Loop ────────┐
        │                                         │
        │  分析 historical F2P                    │
        │          ↓                              │
        │  理解原测试 behavioral intent           │
        │          ↓                              │
        │  识别 implementation binding            │
        │          ↓                              │
        │  找到 public / observable behavior      │
        │          ↓                              │
        │  编写 functional verifier               │
        │          ↓                              │
        │  semantic self-review                   │
        │  - 是否由 P 支持                        │
        │  - 是否错误继承 R/I/Gold 约束           │
        │  - 是否仍绑定特定实现                   │
        │          ↓                              │
        │  submit revision                        │
        │          ↓                              │
        │  ② HARD VALIDATOR [SCRIPT]              │
        │  - artifact/schema/accounting           │
        │  - verifier runnable                    │
        │  - Base + Functional → FAIL             │
        │  - Gold + Functional → PASS             │
        │  - 原始 P2P 原样保留并 PASS     │
        │          │                              │
        │      FAIL ─→ feedback → REPAIR ─────────┘
        │
        └──────────────── PASS ───────────────────┐
                                                  ▼
                                         ③ VERIFIER QA
                              ┌───────────────────┴───────────────────┐
                              ▼                                       ▼
                       POSITIVE QA                              NEGATIVE QA
                  [mini session + Judge]                  [mini session + Judge]
                              │                                       │
                   可参考 Gold 构造                         从 Gold / accepted
                   不同的正确实现                            positive 构造 near-correct
                              │                                       │
                              ▼                                       ▼
                     fresh Judge 确认                         fresh Judge 确认
                   满足 P 且实现实质不同                    确实违反某个 P semantic
                              │                                       │
                              ▼                                       ▼
                       paired replay                            hard replay
                    ┌─────────┴─────────┐                           │
                    ▼                   ▼                           ▼
             Original verifier   Functional verifier         Functional verifier
                 PASS/FAIL           必须 PASS                  必须 FAIL
                    │                   │                           │
                    └─────────┬─────────┴──────────────┬────────────┘
                              │                        │
                         verifier OK?             verifier defect?
                              │                        │
                             YES                      YES
                              │                        │
                              ▼                        ▼
                       ④ PACKAGE FINAL          Converter REPAIR
                           [SCRIPT]                   │
                              ▲                       ▼
                              └──── Validator ← new revision
                                         │
                                   Replay existing QA
```

## 4.3 Functional Converter `[mini-swe-agent]`

Converter 是 Stage 2 的核心创造角色。

它可以读取完整 construction evidence：

```text
P / R / I
historical F2P / P2P
Gold
Repo
Original verifier
Environment
```

P2P 是已通过 oracle 的原始回归集合，必须在最终 config 中按原顺序、原 selector 字符串逐项保留。不得映射类限定名称、删除、排除或替换 P2P。Stage 2 只转换 historical F2P；由 F2P 转换出的 Base regression 可追加在原始 P2P 之后，但不能改动原清单。

Converter 的任务不是机械改写测试，而是对 historical F2P 逐条完成：

```text
historical test
      ↓
这个测试真正想验证什么？
      ↓
该行为是否由 P 支持？
      ↓
原测试绑定了哪些内部实现？
      ↓
是否可以通过 public / observable behavior 验证？
      ↓
生成新的 functional verifier
```

主要产出：

```text
functional verifier
conversion_trace.json
revision artifacts
trajectory / self-review evidence
```

`conversion_trace.json` 至少记录：

```text
source_f2p
historical_behavior
P_support
binding_detected
observable_surface
decision
emitted_test
rationale
```

## 4.4 Hard Validator `[SCRIPT]`

每个 revision 只验证一次。

验证内容：

```text
artifact/schema/accounting 是否完整
verifier 是否可运行

Base + Functional        → FAIL
Gold + Functional        → PASS

原始 P2P 原样保留并 PASS
```

如果失败，将真实执行结果回传 Converter，进入 `REPAIR`。

不再在 Converter 退出后重复运行完全相同的 Final Gate。

## 4.5 Positive QA

目的：验证 functional verifier 是否允许其他满足 P 的正确实现。

Positive Generator 可以参考 Gold，因为这里评估的是 verifier，而不是 solver 本身。

要求构造：

```text
满足 P
且与 Gold 有实质实现差异
```

然后由 fresh Judge 确认：

```text
candidate 确实满足 P
candidate 不是 Gold 的表面重写
```

Confirmed valid alternative 对同一个 patch 同时执行：

```text
Original verifier
Functional verifier
```

要求：

```text
Functional verifier → PASS
```

同时记录 paired verdict：

```text
Original PASS / Functional PASS
Original FAIL / Functional PASS
Original PASS / Functional FAIL
Original FAIL / Functional FAIL
```

其中：

```text
Original FAIL + Functional PASS
```

记为 **rescued valid solution**。

需要统计：

```text
generated_positive_count
confirmed_valid_count
original_pass_count
original_fail_count
functional_pass_count
functional_fail_count
rescued_valid_solution_count
```

注意：

> `rescued_valid_solution_count` 是研究指标，不是转换通过门槛。

如果 Original 本身已经接受 alternative solution，`Original PASS + Functional PASS` 也是正常的 Positive QA 结果。

## 4.6 Negative QA

目的：验证 functional verifier 不会过松。

从 Gold 或 accepted positive implementation 出发，构造 near-correct mutant：

```text
只破坏一个明确由 P 定义的 semantic
其他行为尽量保持正确
```

fresh Judge 确认：

```text
mutant 确实违反 P
不是无关 crash
不是环境问题
```

然后要求：

```text
Functional verifier → FAIL
```

## 4.7 Repair 规则

只有出现明确 verifier defect 才进入 Repair：

```text
confirmed valid positive
+ Functional FAIL
→ false negative

confirmed invalid mutant
+ Functional PASS
→ false positive
```

Repair 后：

```text
Converter REPAIR
→ submit new revision
→ Hard Validator
→ replay 已有 Positive / Negative QA
```

不需要重新生成所有 QA case。

## 4.8 Package Final `[SCRIPT]`

Stage 2 全部通过后才生成正式完成体：

```text
tasks/<id>/final/
├── task.toml
├── instruction.md      # Problem Statement only
├── environment/
├── tests/              # Functional verifier
└── solution/
```

其中：

```text
final/instruction.md
= Problem Statement
```

由确定性逻辑写入，不由 Converter 重写。

`environment/`、`solution/` 和 task 配置原则上复用 original；只有 functional verifier 确实要求时才做最小必要调整，并记录差异。

## 4.9 Stage 2 最简逻辑

```text
Converter [MSA]
BUILD / REPAIR
      ↓
Hard Validator [SCRIPT]
   FAIL ─────→ Converter REPAIR
      │
     PASS
      ↓
Positive + Negative QA
[MSA + Judge + SCRIPT]
      │
 verifier defect?
      ├─ YES → Converter REPAIR → Validator → Replay QA
      └─ NO
           ↓
Package Final [SCRIPT]
           ↓
      final Harbor task
```

# 5. Stage 3：A / B / C 对比评测

## 5.1 目标

Stage 3 不再修改 verifier，只做统一条件下的对比评测。

回答两个问题：

```text
A → B：
去掉原 SWE-Pro instruction 中的 R / I 后，
同一 solver 表现发生什么变化？

B → C：
在 instruction 完全相同的情况下，
将 Original verifier 换成 Functional verifier 后，
判定发生什么变化？
```

## 5.2 三个实验条件

| Condition | Instruction | Verifier |
|---|---|---|
| A Original | 原始 P + R + I | Original |
| B P-only | P only | Original |
| C Functional | P only | Functional |

其中：

```text
B 和 C 使用完全相同的 final/instruction.md
```

因此：

```text
A → B = instruction effect
B → C = verifier effect
```

## 5.3 Pipeline

```text
Stage 2 completed instance
        │
        ▼
① MATERIALIZE CONDITIONS
   [SCRIPT]
        │
        ├───────────────────────────────────────┐
        │                   │                   │
        ▼                   ▼                   ▼
   A ORIGINAL          B P-ONLY          C FUNCTIONAL

 instruction:          instruction:       instruction:
 original/             final/             final/
 instruction.md        instruction.md     instruction.md

 verifier:             verifier:          verifier:
 original/tests        original/tests     final/tests

 environment: SAME
 base repo:    SAME
        │                   │                   │
        └───────────────────┼───────────────────┘
                            ▼
② UNIFIED SOLVER EVALUATION
   [HARBOR + SAME AGENT]
                            │
                  same mini-swe-agent
                  same LLM / model
                  same reasoning effort
                  same timeout
                  same network policy
                  same rollout count
                  same environment image
                            │
                            ▼
                   保存 trajectory / patch
                            │
                            ▼
③ CONDITION-LEVEL RESULTS
   [SCRIPT / HARBOR]
                            │
                  A / B / C success results
                            │
                            ▼
④ PAIRED VERIFIER RE-GRADE
   [SCRIPT]
                            │
                 对 B 条件 P-only rollout patch
                            │
               ┌────────────┴────────────┐
               ▼                         ▼
       Original verifier          Functional verifier
               │                         │
               └────────────┬────────────┘
                            ▼
                    paired verdict matrix
                            │
                            ▼
⑤ AGGREGATE ANALYSIS
   [SCRIPT]
```

## 5.4 B 条件不长期保存第三份正式数据

B 只在评测时临时 materialize：

```text
original/
+ replace instruction.md with final/instruction.md
→ temporary P-only task
```

因此长期正式保存的完整任务只有：

```text
original/
final/
```

## 5.5 统一 Solver 条件

A / B / C 必须固定：

```text
Harbor version
mini-swe-agent scaffold
LLM / model
model configuration
reasoning effort
timeout
network policy
rollout count
environment image
```

不得因为 Functional task 是新构造的，就顺便改变 solver scaffold 或运行环境。

## 5.6 Paired Re-grade

对 B 条件生成的同一个 patch：

```text
P-only instruction
        ↓
same solver rollout
        ↓
candidate patch
        │
        ├─ Original verifier
        └─ Functional verifier
```

得到：

| Original | Functional | 解释 |
|---|---|---|
| PASS | PASS | 两套 verifier 一致接受 |
| FAIL | PASS | functional verifier rescue |
| PASS | FAIL | functional verifier 更严格，需要检查 |
| FAIL | FAIL | 两套都拒绝 |

这样可以排除不同 rollout 带来的 sampling 差异，直接观察 verifier 本身的影响。

## 5.7 Stage 3 主要统计

### Instruction effect

```text
A vs B
```

关注：

```text
success rate
trajectory / token / runtime
failure category
```

### Verifier effect

```text
B vs C
```

关注：

```text
Original verifier verdict
Functional verifier verdict
```

### Paired verdict change

```text
Original FAIL → Functional PASS
Original PASS → Functional FAIL
Both PASS
Both FAIL
```

并与 Stage 2 的：

```text
confirmed valid alternative
Original FAIL
Functional PASS
```

结合分析。

## 5.8 Stage 3 原则

Stage 3 是冻结后的评测阶段：

> 不在 Stage 3 内直接 Repair verifier。

如果发现系统性 verifier defect，应将任务退回 Stage 2 修复，重新冻结 `final/` 后，再重新进行 Stage 3。

# 7. 各目录职责

## `original/`

官方 SWE-Bench Pro V2 task 的完整副本。

原则：

```text
只读
不修改
```

用途：

```text
Stage 1 Oracle preflight
Stage 2 construction evidence
Stage 3 A 条件
Stage 3 B 条件中的 Original verifier
```

## `final/`

Stage 2 转换完成后的完整 Harbor task。

用途：

```text
Stage 3 B 条件中的 P-only instruction
Stage 3 C Functional task
后续独立发布 / 移动 / 批量评测
```

只保存构造、验证、QA 和评测过程，不属于最终 benchmark task。

包含：

```text

converter trajectories / revisions

positive / negative QA
A/B/C evaluation
paired re-grade
controller state
```

```text
│ C Functional                                │
│                                             │
│ Same Harbor + Same Agent + Same LLM         │
│       ↓                                     │
│ Independent eval + Paired re-grade          │
│       ↓                                     │
│ Aggregate analysis                          │
└─────────────────────────────────────────────┘
```

---

# 10. 推荐实现顺序

按阶段实现，不跨阶段提前铺太多逻辑。

## Phase 1：先打通 Stage 1

目标：

```text
给定 1 个 instance_id
→ 获取 original task
→ lazy pull image
→ Base FAIL
→ Gold PASS
→ provenance 完整
```

Stage 1 稳定后再进入下一步。

## Phase 2：实现 Stage 2 的最小闭环

先实现：

```text
Converter
→ Hard Validator
→ Repair
→ final/
```

再加入：

```text
Positive QA
Negative QA
QA-triggered Repair
```

## Phase 3：最后实现 Stage 3

在至少 1 条 `final/` task 通过 Stage 2 后，再实现：

```text
A / B / C materialization
same-agent evaluation
paired re-grade
aggregate report
```

这样可以避免在转换框架尚未稳定时提前编写大量评测层逻辑。

# 11. 最终实验定义

整个实验可以概括为：

```text
Stage 1
验证 source task 是否可信、可执行
        ↓
Stage 2
将 historical verifier 转换成
P-aligned functional verifier
并证明其 acceptance breadth / rejection ability
        ↓
Stage 3
在完全统一 solver 条件下比较：

A = P+R+I + Original verifier
B = P only + Original verifier
C = P only + Functional verifier
```

其中：

```text
A → B
= instruction augmentation effect

B → C
= verifier effect
```

而 Stage 2 Positive QA 中：

```text
confirmed valid alternative
Original FAIL
Functional PASS
```

提供 task-level 的 verifier false-negative repair 证据，与 Stage 3 的 paired re-grade 一起构成最终分析基础。
