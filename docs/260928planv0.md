## 0. 一页摘要

### 目标

把 SWE-Bench Pro V2 的可执行 Harbor task 转换为 **DeepSWE-like 的功能验证任务**：保留 V2 已经整理好的任务环境、Harbor packaging、reference solution、regression infrastructure 和 locked evaluation protocol，重点只研究 **historical F2P → implementation-independent functional verifier** 的转换。

本版最重要的规范变化是：

> **最终 solver-facing instruction 只使用原始 Problem Statement（P）。Requirements（R）和 Interface（I）不参与 instruction 重写，也不提供给 Converter、Semantic Judge、Positive Solver 或最终 solver。**

原因是 R/I 本身就是 SWE-Bench Pro 为了减少 inherited tests 的 false negative 而人工补充的内容，其中可能包含由 Gold patch 或 test expectation 反向塑造出的接口和实现约束。为了避免这些信息经过 LLM “自然语言化”后继续泄露到新任务中，本实验不再做 `P + R + I → instruction` 的综合。

因此新框架的规范关系固定为：

```text
Problem Statement
      ↓
唯一 solver-facing normative specification
      ↓
原样进入 instruction.md（仅做确定性格式规范化）

historical F2P
      ↓
conversion evidence：帮助理解过去验证了什么
      ↓
只有能够追溯到 Problem Statement 的语义才允许进入新 verifier

P2P
      ↓
regression evidence

Gold/reference solution
      ↓
known-correct validation evidence，只用于确定性 Base/Gold replay

Requirements / Interface
      ↓
construction 中完全隔离
仅保留为 research-only metadata，后续可做统计分析
```

最终输出仍然是 Harbor-native task，并使用官方 Harbor / locked protocol 跑真实 solver，形成：

```text
SWE-Bench Pro V2 task
        ↓
F2P verifier transformation
        ↓
functional verifier QA
        ↓
Harbor-native final task
        ↓
locked solver rollout
        ↓
fresh-sandbox re-grade
```

### 成功定义

一个实例只有同时满足以下条件才算转换成功：

```text
官方原始 V2 task 可运行
→ Problem Statement 被原样冻结为最终 instruction
→ 每条新 verifier 语义都可 trace 到 P
→ 每条 historical F2P 都有 conversion accounting
→ deterministic sanity PASS
→ Semantic Judge PASS
→ Base/Gold Core Gate PASS 且重复稳定
→ Positive / Negative QA 达标
→ Harbor package smoke PASS
→ 至少完成一次 locked solver rollout + fresh-sandbox re-grade
```

如果 Problem Statement 本身不足以支撑一个可靠的 functional verifier，**淘汰该 instance，而不是使用 R/I 补全 specification**。

## 1. 实验目的与研究问题

### 1.1 实验目的

SWE-Bench Pro V2 已经把原来的 dataset row、环境、测试执行、reference solution 和 grading protocol 组织成可独立运行的 Harbor task。新项目不再重新解决 V1 中大量的基础设施问题，而是把研究范围收缩到 verifier transformation 本身。

核心目标是：

> **在不使用 Requirements、Interface 和 Gold implementation 来扩张任务规范的前提下，根据 Problem Statement 与 historical F2P evidence，将 inherited implementation-bound tests 转换为基于 public API / observable behavior 的 functional verifier，并验证它既能接受不同正确实现，也能拒绝不完整或错误实现。**

### 1.2 核心研究问题

1. historical F2P 中哪些 assertion 真正对应 Problem Statement 中的功能语义？
2. 哪些 F2P 只是历史实现、private helper、文件布局、mock shape 或特定接口选择的偶然产物？
3. 去掉 R/I 后，Problem Statement 是否仍足以形成可验证的 functional task？
4. 转换后的 verifier 是否接受与 Gold 结构不同但满足 P 的 alternative implementation？
5. 转换后的 verifier 是否能够拒绝仅违反一个已声明功能语义的 semantic mutant？
6. 最终转换任务是否能直接通过 Harbor / locked protocol 被真实 coding agent 求解和评分？

### 1.3 本实验明确不做什么

V2/Harbor 已经负责的内容原则上不重新实现：

- 不从 repo 猜安装和测试命令；
- 不重新实现 Python / Node / TypeScript / Go 通用 runner；
- 不重新 materialize repository 作为主流程；
- 不重新设计一套 task packaging；
- 不重新实现 agent evaluator 或 locked grading；
- 不让 Converter 自己决定 Docker、cwd、service bootstrap 或 test parser；
- 不让 LLM 综合 R/I 生成新的 solver instruction。

## 3. 信息边界：本版最重要的设计

### 3.1 Normative specification

唯一 normative specification：

```text
Problem Statement only
```

最终 `instruction.md` 不经过 LLM 改写：

```text
HF / V2 Problem Statement
        ↓
deterministic normalization
（换行、编码、文件结尾等）
        ↓
final_task/instruction.md
```

不允许：

```text
P + R + I → LLM summary → instruction
P + test expectations → instruction
P + Gold → instruction
```

### 3.2 Role visibility

| 角色 | 可见 | 不可见 |
|---|---|---|
| Converter | Problem Statement、Base repo、historical F2P/test patch、必要公开 repo 文档 | R、I、Gold patch、reference solution |
| Semantic Judge | P、Base repo、F2P seeds、converted verifier、conversion trace、sanity evidence | R、I、Gold |
| Positive Solver | **与最终 solver 尽量一致：P + Base repo** | F2P、P2P、verifier、R、I、Gold |
| Solution Judge | P、Base repo、candidate patch、candidate execution evidence | R、I、Gold、historical test expectations |
| Mutation Generator/Judge | P、accepted positive、已确认的 converted behavioral mapping | R、I、Gold；默认不依赖 historical implementation shape |
| Deterministic controller | 全部 construction artifacts | — |
| 最终 benchmark solver | final `instruction.md` + task environment | hidden verifier、R、I、Gold |

### 3.3 R/I 的处理

R/I 不删除于原始数据集，但从 construction path 隔离：

```text
source_snapshot/
├── allowed/
│   ├── problem_statement.md
│   ├── f2p_seeds.json
│   ├── original_test.patch
│   └── repo metadata
└── research_only/
    ├── requirements.md
    ├── interface.md
    └── augmentation_hashes.json
```

`research_only/`：

- 不 mount 给 Converter；
- 不 mount 给 Semantic Judge；
- 不 mount 给 Positive/Mutation QA agent；
- 不进入 final task；
- 仅供实验结束后的离线统计，例如研究“有多少 V2 augmentation 超出了 P”。

### 3.4 Gold 的处理

Gold/reference solution 只用于 deterministic validation：

```text
Base + new verifier → 应 FAIL
Gold + new verifier → 应 PASS
```

Gold 不提供给 Converter/Judge，不允许用于：

- 定义 public API；
- 决定新 helper 名称；
- 决定文件布局；
- 决定算法；
- 生成 instruction；
- 判断 alternative solution 是否“长得像正确答案”。

### 4.2 Functional verifier artifact

```text
verifier/
├── run.sh
├── manifest.json
├── conversion_trace.json
├── p_coverage_trace.json
```

#### `conversion_trace.json`

每条 historical F2P 必须有 accounting：

```text
source_test_id
historical_behavioral_intent
p_support
binding_detected
observable_surface
decision:
  rewrite
  merge
  drop_out_of_scope
  drop_implementation_bound

```

核心规则：

> `p_support` 无法成立的 F2P 不能偷偷进入新 verifier。

#### `p_coverage_trace.json`

仅分析 Problem Statement，不读取 R/I：

```text
p_claim_id
problem_statement_span
behavioral_claim
supporting_f2p_ids
emitted_functional_tests
status:
  covered
  partially_covered
  unsupported_by_historical_f2p
  non_testable
rationale
```

它回答两个不同的问题：

```text
conversion_trace：每条旧 F2P 去哪里了？
p_coverage_trace：P 中的功能要求被新 verifier 覆盖到什么程度？
```

如果 P 中存在核心功能要求，而 historical evidence 完全不足以形成可信 verifier，则标记 `SPEC_INSUFFICIENT`，该 instance 不发布，而不是读取 R/I 补齐。

## 5. 新 Pipeline

```text
① INGEST / OFFICIAL PREFLIGHT
            ↓
② VERIFIER CONVERTER
            ↓
③ DETERMINISTIC SANITY + P TRACE CHECK
            ↓
④ SEMANTIC JUDGE
            ↓
⑤ CORE GATE
            ↓
⑥ POSITIVE / NEGATIVE QA
       ↘ REPAIR ↗
            ↓
⑦ HARBOR PACKAGE + PACKAGE SMOKE
            ↓
⑧ REAL SOLVER EVALUATION
```

相比上一版，删除了独立的 **Instruction Reconstruction**：instruction 由 deterministic code 直接从 P 产生，不让 LLM 改写。

### 5.1 ① INGEST / OFFICIAL PREFLIGHT

职责：只冻结输入并验证官方任务本身可执行。

步骤：

1. 定位 `v2/tasks/<instance_id>`；
2. 读取官方 `task.toml`、`environment/`、`tests/`、`solution/`；
3. join 对应 HF row；
4. 从 construction 视图中剥离 R/I；
5. 将 Problem Statement 原样写入 `source_snapshot/allowed/problem_statement.md`；
6. 保存 historical F2P/test patch；
7. P2P 保存为 deterministic regression evidence，不给 Converter；
8. Gold/reference 只保留在 controller-private validation area；
9. 记录 repo commit、HF revision、Harbor commit、image digest；
10. 使用官方 V2 protocol 做 oracle preflight：
   - empty/Base 不应通过原始任务；
   - reference solution 应通过原始任务；
11. 失败属于 `PREFLIGHT/INFRASTRUCTURE`，Converter 不得绕过。

本阶段不做：

- ExecutionSpec discovery；
- selector normalization 重实现；
- repo materialization 重实现；
- Python/Node/Go runner discovery。

### 5.2 ② VERIFIER CONVERTER

Converter 只做 verifier transformation，不写 instruction。

输入：

```text
Problem Statement
Base repo
historical F2P/test patch
必要公开 repo 文档
```

输出：

```text
functional verifier
conversion_trace.json
p_coverage_trace.json
coverage_matrix.md
self_review.md
```

对每条 F2P 按以下顺序判断：

```text
historical assertion
      ↓
它在验证什么行为？
      ↓
该行为是否能直接追溯到 P？
      ├── NO → drop_out_of_scope / spec_gap
      │
      └── YES
           ↓
      是否绑定 private helper / file layout /
      internal state / mock shape / Gold structure？
           ├── YES → 重写为 public/observable check
           └── NO  → 可保留功能语义，但不得照搬实现约束
```

允许的 verifier surface 优先级：

- public API；
- CLI；
- HTTP/service interface；
- 文件输入输出；
- externally visible state change；
- 返回值、输出、错误语义。

除非 P 和现有 public repo contract 本身明确要求，否则拒绝：

- private helper；
- unexposed internal field；
- Gold-specific file layout；
- mock call sequence；
- AST/name scan；
- 为通过旧 test 而创造的新接口要求。

### 5.3 ③ DETERMINISTIC SANITY + P TRACE CHECK

继续复用旧框架 deterministic validation 思路。

检查：

- manifest/schema；
- revision/hash；
- 路径安全；
- `run.sh` executable；
- 所有 historical F2P 均有 accounting；
- 所有 emitted functional assertions 均引用至少一个 `p_claim_id`；
- emitted behavior 不得来自 R/I/Gold；
- verifier 不包含 historical selector、Gold path、private helper requirement 等已知 binding；
- `conversion_trace` 与 `p_coverage_trace` 一致；
- 不允许 Converter 把 Docker、Harbor runtime、selector parser 重新塞进 verifier artifact。

### 5.4 ④ SEMANTIC JUDGE

Judge 只看：

```text
Problem Statement
Base repo / relevant public surface
historical F2P evidence
converted verifier
conversion_trace
p_coverage_trace
sanity evidence
```

不看：

```text
Requirements
Interface
Gold/reference solution
```

Judge 主要判断：

1. 每个新 assertion 是否真的可由 P 支持；
2. historical implementation detail 是否被错误升格为规范；
3. public/observable surface 是否合理；
4. P 中的重要行为是否因转换而意外丢失；
5. 当前 instance 是否已出现 `SPEC_INSUFFICIENT`，不应继续包装。

输出：

```text
PASS
REPAIR
REJECT_SPEC_INSUFFICIENT
MALFORMED / INFRASTRUCTURE
```

### 5.5 ⑤ CORE GATE

底层尽量复用官方 Harbor task execution，而不是旧自研多语言 adapter。

默认重复至少两次：

```text
Base + functional verifier        → FAIL
Gold + functional verifier        → PASS
Base + retained P2P               → PASS
Gold + retained P2P               → PASS
```

其中：

- functional verifier 是转换 acceptance gate；
- P2P 是 regression gate；
- historical F2P 仅作 diagnostic replay，不作为 alternative-solution hard gate；
- Gold 只用于这一步的 known-correct smoke。

### 5.6 ⑥ POSITIVE / NEGATIVE QA

#### Positive QA

Positive candidate 应尽可能模拟真实 solver，而不是“看答案写答案”。

Generator/Solver 输入：

```text
final Problem Statement
Base repo
```

不提供：

```text
R/I
Gold
historical F2P/P2P
current verifier
conversion trace
```

步骤：

1. 生成 candidate patch；
2. deterministic execution 检查 candidate 可运行、P2P 通过；
3. Solution Judge 只根据 P、repo 和 candidate behavior 判断是否为 `VALID_ALTERNATIVE`；
4. 如果 Judge 判定合法，而 current functional verifier FAIL：
   - `VERIFIER_FALSE_NEGATIVE`
   - 回到 Converter REPAIR；
5. accepted positive 进入 immutable QA evidence，后续 revision 必须 replay。

第一阶段目标：至少 1 个 accepted positive。

#### Negative QA

从 accepted positive 优先生成 mutant；只有没有 positive 时才允许从其他已验证实现构造，并记录来源。

Mutation Generator 可以看到：

```text
P
accepted positive
已确认的 behavioral mapping
```

但仍不读取 R/I。

每个 mutant 只破坏一个 P-supported semantic：

```text
mutant runnable
P2P PASS
Mutation Judge = RELEVANT_NON_EQUIVALENT
functional verifier → 必须 FAIL
```

若 mutant 仍 PASS：`VERIFIER_FALSE_POSITIVE` → REPAIR。

第一阶段目标：至少 2 个 accepted semantic mutants。

## 6. Harbor-native Packaging 与真实评测

### 6.1 Final task 不再重新发明格式

直接以 V2 Harbor task 为骨架：

```text
final_task/
├── task.toml                 # 尽量复用官方配置
├── instruction.md            # = Problem Statement only
├── environment/              # 复用官方环境
├── solution/                 # 保留为 benchmark construction/oracle 资产
└── tests/
    ├── test.sh               # Harbor-compatible wrapper
    ├── functional/           # converted functional verifier
    ├── upstream/             # retained official regression assets
    └── config.json
```

最终 solver 不应获得 `solution/` 或 hidden verifier 内容；是否物理保留在 task bundle 取决于 Harbor 的标准隐藏/挂载方式，evaluation layer 必须遵守官方 locked protocol。

### 6.2 Package smoke

在 clean/pristine environment 中：

1. 应用 reference solution；
2. 安装最终 converted verifier；
3. 运行 retained P2P；
4. 执行最终 `tests/test.sh`；
5. 检查报告格式、返回码和重复稳定性。

Package smoke 只证明 task wiring + known-correct solution，不证明 verifier acceptance breadth；后者由 Positive/Negative QA 负责。

### 6.3 Real Solver Evaluation

新增独立 `evaluation/` 层，直接调用官方 Harbor / V2 locked tooling。

至少支持：

```text
Oracle smoke
LockedMiniSwe baseline
Optional: LockedCodex / 官方支持的其他 adapter
```

最终链路：

```text
final Harbor task
       ↓
locked solver rollout
       ↓
model.patch
       ↓
fresh pristine grading sandbox
       ↓
functional verifier + retained P2P
       ↓
PASS / FAIL
       ↓
trajectory + patch + verifier logs
```

solver success/failure 与 verifier quality 分开报告，不能互相替代。

## 11. 关键风险与控制

| 风险 | 控制措施 |
|---|---|
| R/I 通过 prompt 间接泄漏实现 | R/I 不提供给任何 construction LLM；final instruction 直接等于 P |
| Gold 影响 verifier 设计 | Gold 仅 deterministic replay 可见，Converter/Judge 不可见 |
| historical F2P 超出 P | 每条 F2P 强制 `p_support`；无支持则 drop/spec_gap |
| P 本身 underspecified | `SPEC_INSUFFICIENT`，淘汰实例，不用 R/I 补齐 |
| verifier 仍绑定 historical implementation | Semantic Judge + solver-view Positive QA |
| verifier 太宽 | targeted semantic mutants |
| Positive candidate 被 verifier prompt 污染 | Positive Solver 不看 verifier/F2P/P2P/Gold |
| 又陷入跨语言 runner 工程 | 执行层优先直接复用 V2 Harbor task protocol |
| package 能运行但真实 agent 不能用 | 必须完成 locked solver rollout + fresh re-grade |
| solver 失败被误认为 verifier 失败 | conversion report 与 solver evaluation 分开 |
| 上游 V2/Harbor 漂移 | 固定 commit/revision/image digest |

## 13. 最终项目定位

> **Swepro_test_trans 是一个基于 SWE-Bench Pro V2 Harbor tasks 的 functional-verifier transformation pipeline。它把原始 Problem Statement 作为唯一 solver-facing normative specification，不使用 Requirements、Interface 或 Gold implementation 补写 instruction；historical F2P 仅作为 verifier conversion evidence，只有能够追溯到 Problem Statement 的功能语义才可进入新 verifier。框架复用 V2 的环境、reference solution、regression infrastructure 和 locked evaluation protocol，通过 Base/Gold replay、solver-view alternative implementations 和 targeted semantic mutants 验证转换后的 verifier，最终输出可由 Harbor 直接运行和评测的 DeepSWE-like functional tasks。**

最小可行路径：

```text
跑通一个官方 V2 task
→ 冻结 P-only source boundary
→ 迁移 Converter / revision / QA
→ F2P → functional verifier
→ P trace + Semantic Judge
→ Base/Gold + P2P Core Gate
→ Positive / Negative QA
→ Harbor-native package
→ LockedMiniSwe rollout
→ fresh-sandbox re-grade
```

这次框架重构的核心不是“重新搭一个 benchmark runner”，而是把基础设施尽量交给 SWE-Bench Pro V2 / Harbor，把研究精力集中在 **P-only specification 下的 verifier transformation 与 verifier quality validation** 上。
