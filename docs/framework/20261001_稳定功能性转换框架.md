# 稳定的 Harbor-to-Harbor 功能性转换框架（2026-10-01）

本文是当前实现的操作说明。`docs/optimize_rule.md` 是转换原则的规范来源；本文说明这些原则如何落到代码和产物。

## 1. 目标和输入输出

输入是 Stage 1 已验证的 Harbor 任务：

- `tasks/<id>/original`：不可修改的原始任务、测试、Requirements、Interface、Gold 和环境；
- `runs/<id>/source/problem_statement.md`：保留给解题者的规范性 Problem Statement；
- 其余 `runs/<id>/source` 文件：只作为 Converter 的 construction evidence。

输出是 `runs/<id>/attempts/attempt_NNN/final` 下的完整 Harbor 任务。最终 instruction 保留原 Problem Statement 及原有通用约束，只在确有产品行为缺口且经过审计时加入行为级补充，不写入 Gold 的类名、方法名、模块路径、签名或算法。

## 2. 一条任务的 pipeline

```text
选择 latest attempt / 新建 attempt
        │
        ▼
mini-SWE Converter（BUILD 或 REPAIR）
  逐条读取 canonical fail_to_pass
  恢复行为意图
  选择 Base 已有的 public / observable surface
  rewrite / merge；必要时提出 behavior-level gap
        │
        ▼
Semantic gate
  schema + P 支持 + Gold-only 绑定检查
        │失败
        └──► structured feedback → 同一 revision 修复或新 revision
        │通过
        ▼
Deterministic artifact gate
  Harbor 文件、F2P 记账、emitted selector、P2P selector、只读边界
        │
        ▼
Docker hard replay
  从 conversion_trace 推导 expectation：
  changed_or_missing → Base FAIL / Gold PASS
  already_satisfies 或纯回归 → Base PASS / Gold PASS
        │
        ▼
Stability replay → Positive QA → Negative QA
        │
        ▼
Acceptance → Package final → final-audit
```

`specification_gap` 只适用于某条 historical F2P 明确断言了可观察产品行为、该行为不在 P 中且缺少规范会妨碍公平转换的情况；它不是发现 P 中其他未测试功能的入口。P 中有、但任何 historical F2P 都没有断言的行为属于本次范围之外，不要求新增测试，也不得作为审计失败。有效的 `specification_gap` 会生成行为级 proposal，补充到下一轮有效 instruction，再要求新的 revision 将该行改为 `p_supported_behavior + rewrite/merge`。只有确实没有独立产品行为的实现细节才允许 `implementation_detail + drop`，并且必须留下证据。

## 3. Converter 的最小决策模型

每条 historical F2P 必须有一行账本，分类与 decision 一一对应：

| 分类 | decision | 含义 |
|---|---|---|
| `p_supported_behavior` | `rewrite` 或 `merge` | P 已描述行为，改用 Base 公共/可观察边界测试 |
| `missing_product_behavior` | `specification_gap` | 行为真实且重要但 P 未写，先补充行为语义再转写 |
| `implementation_detail` | `drop` | 只检查 Gold/内部实现且没有独立产品行为，记录丢弃证据 |

`Base` 中已经存在的 API 名字也不能自动授权任意私有方法或内部结构；反过来，Gold 中新增的类也不能自动成为解题接口。决定依据是行为是否能从产品边界观测，而不是 symbol 是否出现在历史测试里。

## 4. Docker 和路径契约

每个参与者只接收由 `TaskPaths` 解析的 canonical 路径：

- 容器 `/app` 或 `/testbed`：仓库，只读或按 Harbor 运行约定使用；
- verifier `/tests`：只读；
- `/tmp`、日志挂载：临时测试、pytest 日志、parser 输出和缓存；
- revision `tests/`：只存发布的 verifier 文件。

任何组件不得自行猜测 host 路径、从最高编号目录推断最终 revision，或把运行结果写回 `/tests`。接受记录中的 revision 是权威选择；`final-audit` 会优先读取它。

## 5. QA 和语义判定

- Converter 内的 self-review 负责提出候选转换；
- Semantic Judge/semantic audit 负责检查 P 支持、公共面和 Gold-only 绑定；
- Hard Validator 只负责确定性 schema、运行和路径合同；
- Positive QA 验证不同实现仍能通过。若 Base 已满足转换行为，Base 本身可作为独立 positive reference；
- Negative QA 用只违反一个明确行为语义的 mutant，要求 functional verifier 拒绝它。

LLM Judge 的 `UNCERTAIN`、网络失败或协议错误不能被当作语义 PASS。可在本地使用显式 `--deterministic-only` 做可重复审计；这不会伪称为 LLM 判定。

## 6. 发布前自动审计

统一命令：

```bash
PYTHONPATH=src .venv/bin/python -m swepro_trans.validation.final_audit --all-runs --write
```

审计会检查 final 文件、F2P 覆盖、当前 schema、instruction 泄露、Base/Gold expectation、Positive/Negative 候选证据、五类门禁和接受记录，并把结果写到每个 attempt 的 `review/final_audit.json`。旧 schema 只显示 `PASS（legacy）`，不会被静默升级；新任务必须是 current schema 才能进入当前 acceptance。
